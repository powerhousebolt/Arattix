REST API Server

arattix-server (in server/) wraps the library in a production HTTP API, so any language or system can log in to Arattai, send messages and media, broadcast, and receive inbound messages as signed webhooks, without embedding Node.js.

Full documentation This page is an overview. The complete guides live next to the code: server README (architecture, deployment, logging, scaling, runbooks), API reference (every endpoint with cURL examples and response shapes) and library audit (failure domains and how to handle Arattai changes).

Features

  • Persistent sessions: QR login once; the cookie jar is stored encrypted (AES-256-GCM) and restored on restart.
  • Connection lifecycle: DISCONNECTED → CONNECTING → QR_READY → AUTHENTICATED → SYNCING → READY, heartbeat, reconnect with backoff, circuit breaker.
  • Paced sending: queued and throttled (token bucket, per-chat spacing, jitter) to avoid account flagging; Idempotency-Key makes retries safe.
  • Media: multipart uploads streamed from disk to Arattai; downloads streamed back.
  • Broadcasts: chunked sends with delays, per-recipient results, no duplicates after a crash.
  • Webhooks: inbound messages and session events, HMAC-signed (X-Arattai-Signature), retried, SSRF-protected.
  • Admin web UI at /ui/: QR login, chats and replies, sending and broadcasts, tasks with retry and cancel, live logs and events, webhooks, and editable settings.
  • Operations: health and Prometheus metrics, JSON logs with secret redaction, Docker, Compose and PM2 configs, worker failover.
Not available yet The library has no endpoints for group management or reactions. The server's routes for them are validated but answer 501 CAPABILITY_UNAVAILABLE. Inbound messages are discovered by polling, so they arrive a few seconds late.

Quick Start (Docker)

git clone https://github.com/powerhousebolt/Arattix.git
cd Arattix
cp server/.env.example server/.env
# set API_KEYS (openssl rand -hex 24) and MASTER_KEY (openssl rand -hex 32) in server/.env
docker compose --profile server up -d --build server
curl -s localhost:3000/health/ready

Then open http://localhost:3000/ui/ and sign in with one of your API_KEYS.

Without Docker (Node.js 20.6+):

npm install                 # library dependencies (repository root)
cd server && npm ci && npm run build
cp .env.example .env        # set API_KEYS and MASTER_KEY
node --env-file=.env dist/index.js

Logging In

The easiest way is the admin UI: Arattai login → Start QR login, then scan the code shown on the page. With the API:

KEY=your-api-key
# Start a QR login; the response contains the QR as text (qr.data) and as a PNG (qr.dataUrl)
curl -s -X POST localhost:3000/api/v1/auth/session -H "Authorization: Bearer $KEY" \
  | jq -r '.data.result.qr.dataUrl'

# Scan it with the Arattai app, then:
curl -s localhost:3000/api/v1/auth/status -H "Authorization: Bearer $KEY" | jq .data.state
# "READY"

The QR code refreshes itself while you wait; poll GET /api/v1/auth/status to show the current one. After a restart the session is restored automatically. A new scan is needed only when Arattai ends the session (state: "DISCONNECTED", reason: "SESSION_EXPIRED").

Sending

# Text
curl -s -X POST localhost:3000/api/v1/messages/send \
  -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" \
  -H "Idempotency-Key: order-1042" \
  -d '{"chatId":"CT_1350000000000000001_123456789","text":"Your order has shipped."}'

# File (streamed; up to 64 MiB by default)
curl -s -X POST localhost:3000/api/v1/messages/media -H "Authorization: Bearer $KEY" \
  -F chatId=CT_1350000000000000001_123456789 -F caption="Invoice" -F file=@invoice.pdf

# Broadcast in chunks of 10 with 30 s between chunks
curl -s -X POST localhost:3000/api/v1/channels/broadcast \
  -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" \
  -d '{"recipients":["CT_1","CT_2","CT_3"],"text":"Offices closed Monday","chunkSize":10,"chunkDelayMs":30000}'

Sends wait up to 25 s for the result (200). If they are still queued, the answer is 202 with a job id to poll at GET /api/v1/jobs/{id}. Add ?async=true to get the 202 immediately.

Webhooks

curl -s -X POST localhost:3000/api/v1/webhooks/subscribe \
  -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" \
  -d '{"url":"https://crm.example.com/hooks/arattai","events":["message.received","session.state_changed"]}'
# The response includes the signing secret (shown only once).

Verify each delivery before trusting it:

const crypto = require('node:crypto');

function verify(secret, header, rawBody) {
  const parts = Object.fromEntries(header.split(',').map((p) => p.split('=', 2)));
  const expected = crypto.createHmac('sha256', secret).update(`${parts.t}.${rawBody}`).digest('hex');
  const fresh = Math.abs(Date.now() / 1000 - Number(parts.t)) <= 300;
  return fresh && parts.v1?.length === expected.length &&
    crypto.timingSafeEqual(Buffer.from(expected), Buffer.from(parts.v1));
}

Events: message.received, message.sent, message.failed, session.state_changed, session.qr (only when subscribed by name), broadcast.completed, webhook.test.

Deployment Options

SetupCommandWhen
Single processdocker compose --profile server up -d serverOne host, no Redis
Split (Redis + API + worker)docker compose -f server/docker-compose.yml up -d --buildScale the API, survive restarts with queued jobs, worker failover
PM2pm2 start server/ecosystem.config.cjs --only arattix-api,arattix-workerBare-metal / VM; API in cluster mode, one worker
One session, one worker An Arattai account is a single cookie session. Exactly one worker process may own it; a Redis lease enforces that, and extra workers wait on standby. API processes hold no session and can be scaled freely.
